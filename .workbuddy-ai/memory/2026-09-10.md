## 按键 + LED 的 FreeRTOS 任务（已实现并编译通过）

- 硬件（正点原子精英版 V2）：LED0=PB5、LED1=PE5（低电平点亮）；KEY0=PE4、KEY1=PE3（低电平按下）、KEY_UP=PA0（高电平按下）。
- 采用**中断方式**：EXTI 回调里只 `xQueueSendFromISR` 发事件，`KeyTask` 阻塞收队列 → 延时 20ms 消抖 → 确认电平 → 执行动作 → 等松手。LED0 心跳任务 500ms 翻转，可被 KEY_UP 挂起/恢复。
- **关键坑**：CubeMX 把 EXTI 优先级配成 0，FreeRTOS 下调 `xxxFromISR` 会触发 configASSERT 卡死。已在 `USER CODE BEGIN MX_GPIO_Init_2` 里把 EXTI0/3/4 重设为 6（数值须 ≥5）。该块在 CubeMX 生成代码之后执行，重新生成也不会丢。
- 队列 `keyQueue` 在 `USER CODE BEGIN 1`（MX_GPIO_Init 之前）创建，避免中断先于队列就绪。
- 编译结果：RAM 12480B（ucHeap 0x2800 + 任务栈）、FLASH 19448B。
- **协同注意**：用户同时开着 VSCode 编辑 main.c，在"文件已被外部修改"弹窗点了「覆盖」，把 Agent 的改动冲掉了（他当时自己写了个 `vTask1` 翻转 PA5 —— 精英板 LED 实际在 PB5/PE5，PA5 无 LED）。已用 Write 整体重写 main.c 并重新编译通过。
- 后续约定：本工程 main.c 由双方都可能编辑，VSCode 弹窗要点「重新加载」而非「覆盖」。

## 概念讲解（结合本项目）

- 已用图解讲清楚三个点：① 队列 = 数据传递 + 唤醒任务 + 临界保护三合一，所以不用全局变量；② `portYIELD_FROM_ISR` 只置 PendSV 挂起位，真正切换等所有中断退出后做；③ EXTI 优先级：临界区写 BASEPRI=0x50（逻辑 5 左移 4 位）只能挡住数值 ≥5 的中断，0~4 挡不住会破坏内核链表，故 `xQueueSendFromISR` 内 `portASSERT_IF_INTERRUPT_PRIORITY_INVALID()` 触发 configASSERT 冻板。
- 教学偏好确认：用户接受"图解 + 逐行拆解 + 不这么写会怎样"的讲法。

## DHT11 + TFTLCD（ILI9341）FreeRTOS 工程（已建好 BSP，待用户配 FSMC 后上板）

- 需求：温湿度显示到 2.8 寸 TFTLCD，保留 FreeRTOS，删掉之前的 LED/按键两个任务。用户确认：屏幕 ILI9341、英文显示、DHT11 数据脚 **PG9**。
- 新增 `Core/BSP/`：`lcd.h` / `lcd.c`（ILI9341 FSMC 驱动）、`lcdfont.h`（16×24 ASCII 字模，用 PowerShell + .NET System.Drawing 从 Consolas Bold 渲染 0x20~0x7E 共 95 字符，4560 字节进 .rodata）、`dht11.h` / `dht11.c`。
- 顶层 `CMakeLists.txt` 已加 `Core/BSP/lcd.c`、`Core/BSP/dht11.c` 与 include 路径 `Core/BSP`。
- **FSMC 地址映射**：Bank1.sector4 基址 0x6C000000，A10(PG0) 作 RS。16 位总线 HADDR[25:1]→FSMC_A[24:0]，故 A10 落在地址 bit11(0x800)；结构体 RAM 偏移 2 字节，所以基址取 0x800-2 = **0x7FE**，使 `LCD->LCD_RAM` 地址 bit11=1。
- 正点原子精英板 V2 LCD 固定接线（板载排母直插，不用飞线）：CS=PG12(NE4)、RS=PG0(A10)、WR=PD5(NWE)、RD=PD4(NOE)、BL=PB0、D0~D15=PD14/15/0/1/8/9/10 + PE7~PE15。
- DHT11 驱动要点：用 **DWT->CYCCNT** 做微秒延时（HAL_Delay 只有 ms 级）；Cortex-M3 上 DWT 默认关闭，需 `CoreDebug->DEMCR |= TRCENA` + `DWT->CTRL |= CYCCNTENA`。起始信号 20ms 那段用 `vTaskDelay`（可调度），随后 40bit 读取约 5ms 用 `taskENTER_CRITICAL()` 关调度保护。判 0/1 用高电平宽度阈值 40us。
- `DHT11_Init()` 内部有 vTaskDelay，**只能在任务体里调用**，不能放在调度器启动前。
- 任务结构：`Dht11Task`(prio 3, 2s 读一次) → 队列 len=1 + `xQueueOverwrite`（永远只留最新值，永不阻塞）→ `LcdTask`(prio 2, `xQueueReceive` 阻塞等，收到就刷屏)。
- 编译结果：32 目标通过，RAM 12896B / FLASH 28064B；nm 确认 SVC/PendSV/SysTick 仍各一份，ascii_16x24 在 rodata。
- **阻塞项**：用户必须在 CubeMX 里使能 FSMC（Bank1 NE4 / A10 / 16bit）并重新生成，`MX_FSMC_Init()` 才会出现并被 main() 调用；在此之前烧录屏幕不会亮。CubeMX 会自动把 `fsmc.c` + `stm32f1xx_hal_sram.c` 等加进 cmake/stm32cubemx/CMakeLists.txt。
- 精英板 P1/P2 排针引出了 106/112 个 IO，PG9 可用；若不方便可改 `dht11.h` 里的 `DHT11_GPIO_Port/Pin` 宏换任意空闲脚（PG9 在 F1 上是 FSMC_NE2，本项目用 NE4，不冲突）。

## CubeMX 重新生成踩坑 + 根治（重要！）

- 用户在 CubeMX 里配好 FSMC / PB0 / PG9 后点 Generate，结果**整个 Middlewares/ 被清空**。根因：`.ioc` 里 `ProjectManager.DeletePrevious` 被 CubeMX 改回 `true`（我之前手动改过，但每次开 CubeMX 都会被覆盖回 true）。
- **根治办法**：把 FreeRTOS 源码 + FreeRTOSConfig.h 全部从 `Middlewares/FreeRTOS/` 迁到 `Source/Third_Party/FreeRTOS/`，CMakeLists 里同步改路径。`Third_Party/` 不在 CubeMX 的生成清单里，反复 Generate 也不会动。
- `stm32f1xx_it.c` 里 CubeMX 重新加回了 SVC_Handler / PendSV_Handler / SysTick_Handler 三个空函数（与 FreeRTOS 移植层冲突 → multiple definition），再次注释掉。
- FreeRTOSConfig.h 几个小修：
  - `configUSE_16_BIT_TICKS` 与 `configTICK_TYPE_WIDTH_IN_BITS` 在 V11 互斥，只留后者。
  - 加 `configUSE_PREEMPTION 1`（V11 必填）。
  - 加 `configUSE_TIMERS 1`。
  - `configCPU_CLOCK_HZ` 不能用 `SystemCoreClock`（FreeRTOSConfig.h 在 CMSIS 头之前被解析），直接写 `72000000UL`。
- `.ioc` FSMC 实际是配齐了的：NE4=PG12, A10=PG0, NOE=PD4, NWE=PD5, D0~D15=PD0/1/8/9/10/14/15+PE7-15, FSMC 72MHz, AddressSetup=2, DataSetup=4。CubeMX 自动生成 `MX_FSMC_Init()` 和 `HAL_SRAM_MspInit()`。但 .ioc 里 `FSMC.IPParameters` 只列了 3 个时序参数，NE4/MemoryType/DataWidth 是按默认填的（16-bit, LCD type），实际工作。
- 编译结果：RAM 12800B / FLASH 28884B，比之前 12896/28064 略增（FSMC SRAM 驱动 + 1 个空 task 占堆）。
