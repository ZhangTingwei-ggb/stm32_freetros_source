## 教训（重要）

### MADCTL 方向规律（推导过，可复用）
- bit7 MY（行序反）、bit6 MX（列序反）、bit5 MV（行列交换=横屏）、bit3 BGR（本屏必须为 1）。
- **90° 旋转 = MV 置 1 + 恰好一个镜像位**：
  - `0x68` = MV|MX|BGR → 顺时针 90°
  - `0xA8` = MV|MY|BGR → 逆时针 90°
  - `0x28`(MV|BGR) 和 `0xE8`(MV|MX|MY|BGR) 是**镜像**不是旋转，文字会左右反。
- 竖屏：`0x08`（正）/ `0xC8`（倒 180°）。
- 验证模型：`MV=0` 时 物理列=C、物理行=R；`MV=1` 时 物理列=R、物理行=C；
  再按 `MX: 列=239-列`、`MY: 行=319-行` 反转。用 `0x68` 代入：内容左上 (0,0) → 屏右上，
  左上→右上是顺时针 90° 的特征，结论一致。

## 界面越界 bug 复查（2026-09-12，修完构建 FLASH 29240 B）
方向定下来后做了一次全量像素审计，抓出 **3 个横向越界**，都是"字符数数错"造成的：
1. `"Status: WAIT  "` 是 **14** 字符（我当初以为是 12，多打了两个空格）→ 224px，
   从 x=30 起末像素 253 > 239。改成 `"Status: WAIT"`（12 字符，和 OK/ERR 两个状态等宽）。
2. `"ERR:9999"` 是 **8** 字符（我数成 7）→ 128px，从 x=128 起末像素 255 > 239。
   根因是**两个计数器挤一行**：`"OK:1234"`(7) + `"ERR:1234"`(8) = 15 字符 = 240px，
   正好占满屏幕、零余量。**改成一行一个计数器**（y=272 / y=296），都回到 12px 左边距，
   并支持到 5 位数。计数 clamp 到 99999（`%-5lu` 只是最小宽度，不 clamp 会继续变长）。
3. 顺带把状态区整体上移 4px（状态 y 248→244，方块 254→250，计数器 284→272/296），
   让 ERR 那行落在 296..319，正好贴到 320 底边。

### 教训（重要）
- **`"%-4lu"` / `"%2d"` 里的数字是最小宽度，不是最大宽度。** 用它们算布局宽度时
  必须按"最大可能位数"算，否则计数涨上去就会顶出屏幕，而 ILI9341 的地址计数器
  会**回绕到左边**，表现为屏幕上出现乱码而不是简单截断。
- **数中文字符串长度不要靠眼睛。** 我两次把 12 数成 14、把 8 数成 7。
  应该用脚本 `len(s)` 逐条算 `x + len(s)*16*scale - 1 < LCD_W`，并**同时查纵向**。
- 审计脚本本身也有坑：直接把 `"%2d.%d C"` 的字面长度（8）当运行时长度算，
  会误报。必须先按 printf 规则展开成最大输出宽度（`%2d`→2、`%%`→1、`%-5lu`→5）。
- 结论：**改完界面一定要跑一遍宽度审计**，别等用户看到乱码。

### 越界审计工具落地成 skill（`~/.workbuddy-ai/skills/lcd-ui-audit/`）
把这次反复手算的越界检查写成了可复用工具：`SKILL.md` + `audit.py`。
自动从 `lcd.h` 推画布尺寸（会真正求值 `#if ( LCD_MADCTL & 0x20U )` 选分支）、
解析 `#define UI_*`、找出所有 `LCD_ShowString*()` 调用、展开 `snprintf` 格式串，
逐行给结论。用法：`python audit.py Core/Src/main.c`，越界时退出码 1。

**工具本身踩了 3 个坑，全是"静默给错答案"，值得记下来**（都已修，并写进 SKILL.md）：

1. **`0x20U` 的 `U` 后缀把正则打断。** 原来用一条大正则跨全文件匹配
   `#if ... #else ... #endif`，模式写成 `& (0x[0-9A-Fa-f]+)`，遇到 `0x20U` 匹配失败
   → 整块没匹配上 → 回退成"全文件扫 `#define LCD_W`"→ **取到最后一个定义（`#else`
   分支的 320）** → 报出 `0xA8 -> 320 x 240`，和 `lcd.h` 注释里写的 240x320 相反，
   而且不报任何错。修法：mask 用 `[0-9A-Za-z_]+` 匹配再解析；并且改成**逐行维护
   条件栈**，不再用跨行大正则。
2. **`#ifndef __LCD_H` 包含卫哨被误判为假。** 如果 `#ifdef` 拿"全文件宏表"判断，
   `__LCD_H` 在下一行才定义，于是卫哨判假 → **整个头文件内容被跳过** → 又回退到默认值。
   修法：按**文件顺序**记录 `#define`，而不是先收集成集合。
3. **按变量名存格式串，遇到复用缓冲区就错。** `buf` 先后装了温度、湿度、两个计数器，
   按名字索引的 map 会把**最后一次**写进 `buf` 的格式串（`"ERR:%-5lu"`）发给所有调用点，
   于是 2 倍字号那两行被当成 9 字符串量出 288 px，报**假越界**。
   修法：把 `snprintf` 和绘制调用**按源码位置排序**后顺序走一遍，取"该缓冲区最近一次"
   的格式串。

另外把结论从"OK/OVER"两态改成**三态**：`OK` / `TIGHT` / `OVER`。
因为 `%2d` 这种字段宽度只是**最小值**：`"%2d.%d C"` 声明宽度算 6 字符（192 px，安全），
按 `ASSUMED_DIGITS` 最坏 3 位数算 9 字符（288 px，会越界）。DHT11 只报 0~50 °C，
所以真实答案是"安全"。报 OVER 是狼来了，报 OK 又掩盖风险 —— 所以给 `TIGHT`：
不判失败，但要求人工确认取值范围。当前 main.c：**0 越界 / 2 TIGHT**（就是那两行读数）。

**教训**：审计工具必须拿一个已知答案的用例自检。上面 3 个 bug 全都会打印出一张
看起来很正常、其实结论错误的表。自检方法：
`audit.py main.c --width 150` 必须报 OVER 且退出码 1；正常宽度必须退出码 0。
如果窄画布不报错，说明工具坏了，此时的"全绿"毫无意义。

## 屏幕颜色全反（用户报"字体全黑，背景全为白色"）—— 面板极性，已修

**现象**：用户报暗色主题下"字体全黑，背景全为白色"。

**排查过程（关键是排除掉另外两种解释）**：
1. **不是"没烧进去"**：`git show HEAD:Core/BSP/lcd.h` + `git show HEAD:Core/Src/main.c`
   显示**原主题也是暗色**（`LCD_Clear(LCD_COLOR_BLACK)`、蓝标题栏、白字）。
   这块屏从来没有过"白底"版本，所以不可能是旧固件残留。
2. **不是 BGR 位**：BGR（D3）只交换红蓝，颜色会怪，但绝不会把 `0x0000` 变成白。
3. **就是极性反相**：代码里写 `0x0000`，用户看到白色 —— 只有"输出取反"能解释。
   把 11 个主题色按位取反算一遍（脚本），得到：`BG #000000 → #FFFFFF`（纯白）、
   `TITLE → #181008`、`LABEL → #736962`、`TEMP → #004CAC`、`HUMI → #A41839`……
   **全部文字亮度 17~107，整片白底 + 深色字**，和用户描述逐字对上；
   标题栏 `#14171C → #EEE6E6`、分隔线 `#2D3139 → #D5CEC6` 也几乎看不见，
   所以用户看到的就是"一片白 + 黑字"。

**根因**：这块屏是**常白（normally white）面板**，控制器默认把 `0x0000` 显示成白。
而我们的初始化序列（抄 ILI9341 手册的官方 initial sequence）里**完全没有 `0x20`/`0x21`**，
所以手册序列在真·ILI9341 上没问题，在这块屏上就整体反相。

**为什么潜伏这么久**：反相后的画面是"白底 + 深色字 + 浅色标题栏"，
**看起来像一个完全正常的浅色 UI**。原主题（黑底/蓝标题栏/白字）反相后是
"白底/黄标题栏/黑字"，同样像正常界面。用户之前几轮只关注方向（横竖/正反），
没提颜色；直到专门要了暗色主题、期待黑底却看到一片白，才暴露。

**修复**：
- `lcd.h` 新增 `LCD_INVERSION_OFF(0x20)` / `LCD_INVERSION_ON(0x21)` / `LCD_INVERSION`，
  当前定稿 `LCD_INVERSION_ON`，注释里写清"全屏刷 `0x0000` 是白的就是要 ON"。
- `lcd.c` 的 `ILI9341_Init()` 在 COLMOD 之后加一条 `LCD_WriteCmd(LCD_INVERSION)`。
- **二进制级验证**（objdump，不靠读源码）：
  `movs r0, #168 @ 0xa8`（MADCTL）后面紧跟 `movs r0, #33 @ 0x21`（极性），顺序正确。
- 构建通过：RAM 12800 B / FLASH 29196 B（+8 B）。
- `Docs/LCD_Guide.md`：新增 2.6 节讲面板极性（含判定表），3.3 节的"两个必须知道的命令"
  改成三个并加上 `0x20/0x21`，第 5 节故障表新增"颜色全反"一行。

## 按"最小可用"重写 LCD 驱动 + 简化 UI（用户要求"用最简单的方法在 lcd 上展示信息"）

**用户诉求**：不要花哨，驱动只要能把信息显示出来就行。用户此前说过自己完全不懂 LCD 代码，
所以这一版的目标是**代码短到能一眼读完**，不是加功能。

### `lcd.h` / `lcd.c`：对外只剩 3 个函数
```c
void LCD_Init( void );
void LCD_Clear( uint16_t color );
void LCD_ShowString( uint16_t x, uint16_t y, const char *str, uint16_t color );
```
内部 static：`LCD_WriteCmd` / `LCD_WriteData` / `LCD_SetWindow` / `ILI9341_Init` / `LCD_ShowChar`。

**关键简化决策：**
- **文字背景色写死在驱动里**（`LCD_ShowChar` 里用 `LCD_COLOR_BG`），所以 `LCD_ShowString`
  只有 4 个参数。省掉 bg 参数后调用点干净很多；代价是不能在色块上写字，需要时再加回来。
- **删掉 `LCD_ShowCharScale` / `LCD_ShowStringScale`**（放大字体）→ 全屏统一 16x24。
- **删掉 `LCD_Fill`** → 没有色块、没有分隔线。
- **删掉方向自动推导**：`LCD_W`/`LCD_H` 直接写死 240/320，`LCD_MADCTL` 一个宏。
  连带删掉 `main.c` 里的 `#if (LCD_W > LCD_H) #error` —— 那个断言的价值在于"推导可能推错"，
  尺寸写死后就没有可推导错的东西了。
- **调色板从 11 个减到 8 个**：删 `PANEL`/`EDGE`/`MUTED`（只服务标题栏和分隔线），
  `TITLE` 改名 `TEXT`。
- **`LCD_ShowString` 不做自动换行** —— 需要换行就调两次传不同 y。少一个功能少一段要读的代码。
- **`ILI9341_Init` 的魔数序列原样保留**：删它不会报错，但 gamma/电源/VCOM 决定了颜色好不好看。
  简化结构 ≠ 简化能工作的部分。

### `main.c`：UI 从 8 个元素减到 8 行纯文字
删掉标题栏色块、两条分隔线、状态方块。现在每行一个元素，共用左边距 `UI_X = 12`：
```
12   DHT11 MONITOR      64 Temperature   92 23.5 C
136  Humidity          164 45.0 %       216 Status: OK
256  OK:12             288 ERR:0
```
计数器 clamp 从 99999 改成 9999（`"%-4lu"`，固定 8 字符宽，不会变长）。

### 改 main.c 的做法（重要，可复用）
按项目约定**不用 Write 整文件重写**，改用一个字节级替换脚本（用完已删）：
- 先确认文件是**纯 ASCII + 全 CRLF**（`sum(1 for b in d if b>127) == 0` 且 `count(b'\n') == count(b'\r\n')`）。
- 用标记切片替换：`buf.find(开始标记)` 到 `buf.find(结束标记)`，每处断言"标记唯一"。
- **写盘前校验**输出仍是纯 ASCII + 全 CRLF，不满足就中止（第一次跑就靠这个拦住了 bug）。
- **踩的坑**：Python 三引号里的 `\n` 是**裸 LF**，直接 `encode()` 写进 CRLF 文件会变成混合行尾，
  校验直接失败。修法：写回前 `new_text.replace('\r\n','\n').replace('\n','\r\n')`。
  脚本在写盘前中止了，所以文件没被写坏。
