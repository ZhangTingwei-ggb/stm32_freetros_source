- 用户反馈"显示内容要竖着，现在是横着"。

  - `lcd.h` 补 `uint16_t LCD_ReadID( void );` 声明，方便读屏 ID 确认型号。
- `main.c` 的 UI 坐标改成按 `LCD_W > LCD_H` 自动选竖屏/横屏两套布局，改 LCD_DIR 后不用动 main.c。标题栏宽度与居中位置也改成用 LCD_W 计算。

## 重要发现：CubeMX 会破坏 main.c 的中文注释（编码损坏）

- 现象：`main.c` 里所有中文注释变成 `浠诲姟鏍堟寜 word 锟??` 这类乱码。

- **约定：`Core/Src/main.c` 里的注释一律只用英文（ASCII）。** 中文注释放 `Core/BSP/` 和 `Third_Party/` 下的文件里。
- 已重写 main.c：全 ASCII 注释 + UI 布局自适应 + 保留 CubeMX 生成的 MX_FSMC_Init / MX_GPIO_Init 原样。验证非 ASCII 字节数 = 0。

## 找到根因：xQueueCreate() 放在 HAL_Init() 之前 → BASEPRI 永久 = 0x50 → HAL_Delay() 死等

用户报"屏幕全白，连个 led 全亮，不闪"。用 `git diff HEAD` 对比出**已提交版本（HEAD = 9-10 23:06，即"能正常显示"那版）的 LCD 通路与本轮代码逐字节等价**（`lcd.c` 只改了 0x08 → `LCD_MADCTL`（同值）+ 背光顺序 + 自检；`MX_FSMC_Init` / `MX_GPIO_Init` 完全没动）。所以故障不在 LCD 代码，在**启动路径**。

**真正的 bug（本轮修复）：**

```c
int main(void)
{
  /* USER CODE BEGIN 1 */
  dhtQueue = xQueueCreate( 1, sizeof( DHT11_Data_t ) );   /* ← 在 HAL_Init() 之前！ */
  ...
  HAL_Init();
```

`xQueueCreate()` → `pvPortMalloc()` → `vTaskSuspendAll()/xTaskResumeAll()` + `xQueueGenericReset()` → `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`。

- `port.c` 里 `static UBaseType_t uxCriticalNesting = 0xaaaaaaaa;`（哨兵值），只有 `xPortStartScheduler()` 第 400 行才把它置 0。
- 调度器启动前 `taskENTER_CRITICAL()` → `uxCriticalNesting = 0xaaaaaaab`，`portDISABLE_INTERRUPTS()` 把 **BASEPRI = configMAX_SYSCALL_INTERRUPT_PRIORITY = 5**。
- 配对的 `taskEXIT_CRITICAL()` 递减回 `0xaaaaaaaa` ≠ 0 → **`portENABLE_INTERRUPTS()` 永远不会被调用 → BASEPRI 一直保持 0x50**。
- BASEPRI = 0x50 屏蔽所有优先级数值 ≥ 5 的中断 → **HAL 时基 TIM1（TICK_INT_PRIORITY = 15）被屏蔽 → `uwTick` 不再递增 → `HAL_Delay()` 死等**。
- `vPortSVCHandler()` 启动第一个任务时会把 BASEPRI 清零（port.c 第 238 行 `msr basepri, r0`，r0=0），所以**同一个 `HAL_Delay()` 在任务里是好的，在 `main()` 里（调度器启动前）就是死的**。这正是"以前能跑，加了开机自检就白屏"的原因。

**修复：** 把 `dhtQueue = xQueueCreate(...)` 从 `USER CODE BEGIN 1`（`HAL_Init()` 之前）挪到 `USER CODE BEGIN 2`（`MX_FSMC_Init()` 之后、`xTaskCreate()` 之前）。main.c 里写了长注释解释。

**同时改进诊断（`Core/Src/main.c`）：**
- 诊断全部改用 **DWT->CYCCNT** 计时（新增 `DWT_Enable()` / `DelayMs()`），彻底不用 `HAL_Delay()`，这样即使 HAL tick 死了也能把结果报出来。
- `Mark(n)` 打点函数：**同时闪背光(PB0)和 LED1**，300ms 亮/300ms 灭 + 1.2s 组间停。屏幕整片亮暗比小灯好数得多；若只有 LED1 闪而屏不变，说明 PB0 不是背光。
- `ReportId()` 也改成闪背光+LED1；`HalDelayProbe()` 挪到**最后**（HAL tick 若死就会卡在这里，但前面的结果已经报完了）。
- `stm32f1xx_it.c` 的 `HardFault_Handler` 加了陷阱：直接写 `GPIOB->BSRR / GPIOE->BSRR` 让背光+LED1 快速连闪，用来区分"卡死"和"取异常（多为 FSMC 总线错误）"。不用 HAL、不假设栈完好。
- 编译：RAM 12800B / FLASH 29652B。

**方法论收获：这个仓库有 git 历史**（`cecf590 v1` 9-9 / `37e87b7 Create Middlewares` 9-10 18:13 / `06c65f0 freertos` 9-10 23:06 / `b900cfd merge`）。`v1` 是裸 CubeMX 工程（无 LCD）。以后"以前能跑现在不行"直接用 `git diff HEAD -- <file>` 定性，比逐行读快得多。

## 代码回退到 b900cfd（用户要求）+ 修复损坏的 git 对象库

用户要求："把代码恢复到 b900cfd3e41861346b5c5e786267a016d141fa04 对应的代码版本"。

**背景**：`HEAD` 本来就是 `b900cfd`，所以"恢复"= 丢弃工作区改动。但本地 `.git` 对象库已损坏，常规手段全废。

**损坏症状（排查记录）：**
- `git status` / `git read-tree HEAD` / `git checkout b900cfd -- <path>` 全部 `fatal: unable to read tree (0c3c722e...)`。
- `git fetch origin` 报 `Could not read 06c65f0b3c65eeda427f72ab08b83685c454f7ab`（b900cfd 的父提交丢了）。
- `git log --all` 只能列出 5 个 commit 中的一部分。
- `git count-objects -v` → `count: 903, in-pack: 0, packs: 0`（全是松散对象）。
- 但**单文件** `git show <rev>:<path>` 对部分路径仍然可用 —— 这是关键线索。

**用 Python 直接读 `.git/objects` 做对象考古**（绕开 git 的树遍历）：
- 903 个对象 = 752 blob + 146 tree + 5 commit，全部能 zlib 解压。
- tree 对象里存着"文件名 → blob SHA"映射，所以**即使父树丢了，也能从任意一个 tree 里挖出映射**。扫描所有 tree 找到 `Core/BSP` 树 `81c3981407`，拿到 lcd.c/lcd.h/dht11.c/dht11.h/lcdfont.h 的 blob SHA。
- 反向引用查找：`Core` 树 `4ab4cbcc61` 指向 `BSP = 0c3c722e`（**丢失**）、`Src = d57cd3dca4`（存在）。`81c3981407` 和 `3ee67cf7b9` 是**孤儿对象**（无人引用），属于工作区 stash。
- 结论：b900cfd 自己的 `Core/BSP` 树对象被销毁，无法从本地恢复。

**踩的坑（重要教训）：** `git stash push -m ... -- <pathspec>` 在对象库损坏的情况下**把工作区文件截断成了 0 字节** —— `Core/BSP/{lcd.c,lcd.h,dht11.c,dht11.h,lcdfont.h}` 和 `Third_Party/FreeRTOS/FreeRTOSConfig.h` 全变 0 字节，而且它创建的 `stash@{0}` 本身也是坏的（`git stash show` 报 `unable to read tree 1788ba76`）。**对象库有问题时绝对不要 stash。**
- 之前的"校验 OK"是**假阳性**：校验循环复用了同一个会失败的 `git show ... > /tmp/x`，两边都被截断成空，`diff` 自然说一致。教训：校验必须用不会共同失败的方式（比字节数 + 退出码）。

**真正的解法（已验证）：远程仓库是健康的。**
- `origin = https://github.com/ZhangTingwei-ggb/stm32_freetros_source.git`，b900cfd 就是从它 pull 来的。
- `git fetch` 会因缺父提交而失败，但 **`git clone --no-checkout <url> <临时目录>` 成功**（克隆不需要本地对象）。
- 把克隆的 `.git/objects/pack/pack-8ccfcd92*.{pack,idx,rev}` 复制进本地 `.git/objects/pack/` → **本地对象库立刻补齐**：`git ls-tree -r b900cfd` 从 4 个文件变成 967 个，`git cat-file -t 0c3c722e` 返回 `tree`，`git status` 恢复正常。
- 然后 `git reset --hard b900cfd` → `Updating files: 100% (967/967)`，一次成功。
